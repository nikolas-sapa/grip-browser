grip

A CDP-native browser SDK for AI agents. Published on PyPI.

An agent that reads a page usually pays for the whole document. grip sends it the interactive elements and visible text instead, structured and indexable.

pip install grip-browser

One measurement worth arguing about

Same page, same machine, same encoder (tiktoken cl100k_base), measured 2026-08-10.

13,773

Playwright MCP's accessibility snapshot on Hacker News, against 13,701 tokens of raw HTML for the same page.

The accessibility tree came out larger than the markup it was compressing. Not marginally. Larger.

That is not a Playwright bug. It is what happens on link-dense pages. There is very little markup to strip, but every link still needs a role, a name and a ref, so you pay full price for the structure and save almost nothing on the tags. The compression mechanism goes negative.

It means "the accessibility tree is compact" is a property of typical pages, not a property of accessibility trees. On six of our eight pages Playwright MCP wins comfortably. On this one it loses to the markup.

What this does not measure

Payload size only

Nothing about task success, latency, reliability, cross-browser support, or ecosystem size. A smaller payload is not a better tool. If your agent fails the task, the token count of its failure is irrelevant.

Playwright is not bad

It is a general-purpose framework with a far larger ecosystem, and it drives human-written E2E suites across three browsers. grip does one narrow thing. Judge them on the axis you actually need.

A note on browser-use. On a like-for-like payload comparison browser-use comes out at 0.90x of grip's snapshot, so it is smaller. That is because it serialises less of the page, not because it compresses better: on Wikipedia its 6,778 tokens cover a viewport with 26 pages still below it, while grip's 19,946 cover the whole article. Quoting 0.90x without that caveat inverts what the number means.

One of our own runs was wrong. Playwright MCP reported a constant 32 tokens on all eight pages at one point. It was tokenising an error string because the browser was not installed. We caught it, published it, and added a guard. It is in the benchmark file because a number you cannot trust is worse than no number.
